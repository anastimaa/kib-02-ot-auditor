# Руководство пользователя веб-приложения "Аудитор сегментации IT/OT-сетей"

В рамках учебного проекта KIB-02 мы разработали веб-приложение для проверки правил доступа между устройствами офисной и промышленной сети. Оно рассчитано на небольшой производственный объект, где нужно разобраться, какие соединения разрешены в конфигурации, и проверить, не противоречат ли они принятой политике разделения IT- и OT-сегментов.

Для проверки не нужно подключаться к настоящим коммутаторам, межсетевым экранам или промышленным контроллерам: аудитор работает с подготовленным JSON-файлом либо парой CSV-файлов. Мы используем синтетические конфигурации, а вся их обработка выполняется в браузере без отправки файлов на сервер. Результаты можно посмотреть на схеме сети, разобрать по отдельным правилам и сохранить в JSON-отчет.

## Как запустить приложение

Мы предусмотрели три способа запуска. Для обычного знакомства с аудитором проще воспользоваться опубликованной версией на Vercel; при работе с кодом удобнее запускать проект через Vite, а для демонстрации без интернет-соединения можно заранее собрать автономный HTML-файл. Во всех трех случаях проверка конфигураций происходит локально в браузере.

### Вариант 1. Онлайн-демо

Откройте [демо KIB-02](https://kib-02-ot-auditor.vercel.app) в браузере. Устанавливать Node.js, скачивать репозиторий или запускать локальный сервер для этого не нужно: интерфейс уже опубликован и доступен по ссылке. Для первого знакомства достаточно встроенного примера "Учебный завод №1", который загружается автоматически; при необходимости здесь же можно импортировать собственную учебную конфигурацию и скачать отчет о проверке.

На стартовой странице показаны девять разрешенных соединений, из которых три нарушают политику, пять соответствуют ей, а одно требует ручной проверки. Ниже находятся схема IT/DMZ/OT, таблица результатов и сведения о загруженной конфигурации.

### Вариант 2. Локальный запуск через Vite

Этот способ подходит, если нужно посмотреть исходный код, изменить приложение или запустить его у себя на компьютере. Понадобится [Node.js](https://nodejs.org/) версии **24 или новее** (npm устанавливается вместе с ним) и [Git](https://git-scm.com/downloads). На Windows команды можно вводить в PowerShell, Windows Terminal, cmd или Git Bash, а на macOS и Linux — в обычном терминале. После установки Node.js или Git желательно открыть новое окно терминала.

Сначала можно проверить, что программы доступны:

```bash
git --version
node --version
npm --version
```

Затем перейдите в папку, где хотите хранить проект, и выполните команды по порядку:

```bash
git clone https://github.com/anastimaa/kib-02-ot-auditor.git
cd kib-02-ot-auditor
npm ci
npm run dev
```

`git clone` скачает репозиторий, `npm ci` установит зависимости из `package-lock.json`, а `npm run dev` запустит сервер разработки Vite. Терминал напечатает локальный адрес, обычно `http://127.0.0.1:5173/`, который нужно открыть в браузере. Пока приложение запущено, терминал следует оставить открытым; для остановки сервера используется `Ctrl+C`.

Если Git устанавливать не хочется, скачайте исходники на [странице репозитория](https://github.com/anastimaa/kib-02-ot-auditor) через **Code → Download ZIP**, распакуйте архив и откройте терминал в папке с `package.json`. После этого достаточно выполнить `npm ci` и `npm run dev`; требования к версии Node.js остаются такими же.

На Windows PowerShell может блокировать запуск `npm.ps1`. В этом случае можно использовать cmd либо команды `npm.cmd ci` и `npm.cmd run dev`; менять системные настройки безопасности для запуска проекта не требуется.

### Вариант 3. Автономная HTML-версия

Для автономного запуска нужно один раз собрать проект из исходного кода. Сборка создает файл `dist/offline.html`, в который включены интерфейс приложения, стили, JavaScript-код и демонстрационные конфигурации. Готовый файл можно открыть в браузере без сервера и без подключения к интернету, поэтому этот вариант удобен, если нужно показать работу аудитора на другом компьютере.

Скачайте репозиторий через Git или **Code → Download ZIP** и откройте терминал в папке с `package.json`. Для подготовки автономной версии выполните:

```bash
npm ci
npm run build
```

После завершения сборки откройте появившуюся папку `dist` и запустите файл `offline.html` двойным нажатием, при необходимости выбрав Chrome, Firefox, Edge или Safari. Node.js и npm нужны только на этапе сборки, поэтому для последующего открытия готового HTML-файла устанавливать их на другом компьютере не потребуется.

Папка `dist` не включена в GitHub-репозиторий, поскольку создается автоматически. Сразу после скачивания исходников файла `dist/offline.html` там не будет: сначала нужно выполнить `npm run build`. Сам готовый файл при необходимости можно перенести на другой компьютер.

### Проверка тестов и сборка

Из корня проекта можно запустить автоматические проверки и повторить сборку:

```bash
npm test
npm test -- --report
npm run build
```

`npm test` проверяет 20 подготовленных конфигураций и дополнительные случаи, а результат выводит в терминал без изменения файлов проекта. Если нужен новый подробный отчет в `docs/test_results.md`, используется `npm test -- --report`. Команда `npm run build` проверяет TypeScript, собирает веб-версию в `dist/` и создает автономный `offline.html`. Для просмотра собранной веб-версии через локальный сервер предусмотрена команда `npm run preview`.

## Что проверяет аудитор

Рассматривается небольшое предприятие с тремя сетевыми зонами:

| Зона | Что в ней находится | Зачем она выделена |
|---|---|---|
| `IT` | Офисные компьютеры и серверы | Работа сотрудников и обычные корпоративные сервисы |
| `DMZ` | Промежуточный сервер доступа | Контролируемые соединения между офисной и промышленной частью сети |
| `OT` | PLC, HMI, инженерная станция, архив технологических данных | Управление оборудованием и работа производственных систем |

Во входном файле перечислены устройства и правила доступа: действие `allow` разрешает соединение, а `deny` запрещает его. Аудитор последовательно проверяет именно явно заданные разрешения и сравнивает их с условиями учебной политики `KIB-02/1.0`.

Например, прямой доступ офисного компьютера к PLC по TCP/502 относится к нарушениям. А обращение согласованной рабочей станции к серверу доступа в DMZ по TCP/443 соответствует заданному исключению. В обоих случаях программа смотрит не только на порт: имеют значение зона, тип и точный идентификатор устройства.

Результат проверки одного разрешения может быть трех типов:

| Статус в отчете | Обозначение в интерфейсе | Что означает |
|---|---|---|
| `PASS` | Допустимо | Соединение совпало с разрешенным исключением учебной политики |
| `VIOLATION` | Нарушение | Правило противоречит политике сегментации |
| `REVIEW` | На проверку | Данных политики недостаточно для автоматического одобрения либо обнаружено точное противоречие между `allow` и `deny` |

Статус `REVIEW` не означает, что соединение можно считать безопасным или разрешенным по политике: такой случай нужно отдельно разобрать вручную.

## Работа с интерфейсом

### Обзор аудита

При открытии приложения по умолчанию загружается `plant.json` — конфигурация "Учебный завод №1". На странице "Обзор аудита" сразу видны общие показатели, схема соединений, сведения о текущем файле и таблица результатов, поэтому сначала можно изучить готовый пример, а уже потом загружать собственные данные.

Для этого примера программа получает **3 сегмента, 7 устройств и 9 явно разрешенных соединений**. Из них 3 попадают в категорию "Нарушение", 5 — в "Допустимо" и 1 — в "На проверку".

Значение "Проверено правил" относится к явно разрешенным соединениям (`allow`). Запреты `deny` в это число не входят: они учитываются отдельно при поиске точных конфликтов и выводятся во вкладке "Устройства" и в экспортируемом отчете.

### Схема сети

На схеме устройства распределены по трем зонам, а стрелки показывают, от какого устройства к какому разрешено соединение. Цвет каждой стрелки зависит от результата проверки; кнопка "Нарушения" в верхней части схемы позволяет оставить только соединения со статусом `VIOLATION`.

На стрелку можно нажать: откроется карточка соответствующего правила. Кнопка "Нарушения" над **схемой** не меняет фильтр **таблицы** под ней — это две отдельные настройки.

### Таблица и подробности правила

В таблице для каждого разрешения указаны его ID, источник, получатель, протокол, порт и статус. Результаты можно переключать между категориями "Все", "Нарушения", "Допустимые" и "На проверку", а поиск позволяет найти запись по ID правила, устройству или коду политики.

Нажмите на строку `R-01` в исходной конфигурации. Для нее программа укажет направление `PC-01 → PLC-01`, зоны `IT → OT`, сервис `TCP/502` и код `P-01`. Такое разрешение нарушает запрет на прямой доступ из офисной сети к промышленному контроллеру. В карточке также указаны критический приоритет, причина срабатывания и рекомендация.

### Загрузка своей конфигурации

Через кнопку "Загрузить конфигурацию" можно выбрать один JSON-файл или **два CSV-файла одновременно**. В случае CSV файлы должны называться `assets.csv` и `rules.csv`; готовая пара для проверки лежит в папке `examples/`.

После выбора файлов программа проверяет формат данных, обязательные поля, идентификаторы и ссылки на устройства. Если конфигурация корректна, приложение сразу строит новый отчет. Если файл содержит ошибку, на экране появляется сообщение с причиной, а предыдущая успешно загруженная конфигурация остается открытой.

### Примеры без нарушений и с нарушениями

Откройте меню "Выбрать демопример" в блоке "Конфигурация". Там есть два варианта:

- **"С нарушениями"** (`plant.json`) — 9 разрешений, из них 3 с нарушениями и 1 требует проверки.
- **"Без нарушений"** (`approved.json`) — 5 разрешений, все получили `PASS`.

Оба примера включены в приложение, поэтому для переключения не нужно выбирать файлы с компьютера.

### Устройства, политика и журнал

Во вкладке "Устройства" приведен инвентарь из загруженной конфигурации: идентификатор, название, зона и тип устройства. Ниже перечисляются явные запреты `deny`, если они есть. Для исходного `plant.json` таких запретов нет.

Во вкладке "Политика" показаны правила `KIB-02/1.0`, их статусы, причины срабатывания и рекомендации. Там же можно открыть полную спецификацию форматов и порядка проверок.

"Журнал сессии" находится внизу страницы. Он фиксирует основные действия в пределах открытой вкладки, в том числе успешный и отклоненный импорт, а также подготовку отчета. Хранятся последние 50 сообщений; после обновления страницы история не сохраняется.

### Экспорт результатов

После нажатия "Экспорт отчета" браузер скачает файл `kib-02-audit.json`. В нем сохраняются название проверенной сети, версия политики, общая статистика и результаты по всем явно разрешенным соединениям, а исходные запреты `deny` выносятся в отдельный список.

Каждая строка отчета содержит источник и получателя, сервис, статус, код политики, причину и рекомендацию. Экспорт охватывает **все** проверенные разрешения, даже если в таблице включен фильтр или поисковый запрос.

## Как устроена проверка

### Входные данные

**JSON** содержит пять обязательных полей: `schema_version`, `network_name`, `zones`, `assets`, `access_rules`. Поддерживается версия схемы `1.0`. Пример полного файла находится в [`examples/plant.json`](examples/plant.json).

Фрагмент одного правила из этого файла:

```json
{
  "id": "R-01",
  "source": "PC-01",
  "destination": "PLC-01",
  "protocol": "TCP",
  "port": 502,
  "action": "allow"
}
```

Это только одна запись из `access_rules`, а не отдельная конфигурация для импорта. Чтобы загрузить JSON самостоятельно, нужен полный объект с устройствами и зонами.

Для **CSV** требуются два файла в UTF-8. В `assets.csv` указаны устройства, а в `rules.csv` — правила доступа. Заголовки должны совпадать с примерами:

`assets.csv`:

```csv
id,name,zone,type
PC-01,Рабочая станция,IT,workstation
PLC-01,Контроллер,OT,plc
```

`rules.csv`:

```csv
id,source,destination,protocol,port,action
R-01,PC-01,PLC-01,TCP,502,allow
```

При загрузке CSV зоны определяются по столбцу `zone`. Система проверяет, что каждый источник и получатель существует в списке устройств. Максимальный размер каждого файла — **1 МиБ**. Допустимы от 1 до 200 устройств и до 1000 правил. Подробные ограничения описаны в [`docs/specification.md`](docs/specification.md).

### Порядок применения политики

Каждое явно разрешенное соединение проходит одну и ту же последовательность проверок. Срабатывает первое подходящее условие, поэтому у одного разрешения будет один код политики и один статус.

| Код | Когда применяется | Результат |
|---|---|---|
| `C-01` | У разрешения есть точный `deny` с теми же условиями | `REVIEW` |
| `P-06` | Источник `ANY` обращается к PLC | `VIOLATION` |
| `P-01` | Прямой доступ из IT к PLC | `VIOLATION` |
| `P-08` | Используется `ANY` или диапазон портов | `VIOLATION` |
| `P-03` | Согласованный доступ `PC-01 → JUMP-01`, TCP/443 | `PASS` |
| `P-04` | Доступ из `JUMP-01` к `ENG-01` по TCP/3389 или к `HIST-01` по TCP/443 | `PASS` |
| `P-05` | Доступ `HMI-01` или `ENG-01` к `PLC-01` по TCP/502 | `PASS` |
| `P-02` | Другое межсегментное разрешение | `VIOLATION` |
| `P-07` | Другое разрешение внутри одного сегмента | `REVIEW` |

Исключения `P-03`–`P-05` действуют только при совпадении идентификаторов устройств, их зон, типов и сервиса. Если в конфигурации появится похожее устройство с другим ID, разрешение не станет автоматически допустимым.

Запреты `deny` не образуют отдельные строки аудита: они нужны для проверки точного конфликта с `allow` и попадают в соответствующий раздел экспортируемого JSON. Частичные пересечения правил и их порядок в настоящем межсетевом экране программа не анализирует.

### Повторение демонстрации

Если нужно быстро проверить работу приложения, достаточно следующего сценария:

1. Открыть "Обзор аудита" с `plant.json` и проверить числа **3 / 5 / 1** для нарушений, допустимых соединений и ручной проверки.
2. Выбрать `R-01` и посмотреть, почему прямой доступ IT → PLC получил `P-01`.
3. В блоке "Конфигурация" выбрать "Без нарушений". Результат должен измениться на **0 / 5 / 0**.
4. Нажать "Загрузить конфигурацию" и выбрать из `examples/` два файла `assets.csv` и `rules.csv` одновременно. Они должны дать те же результаты, что и `plant.json`.
5. Вернуться к исходному примеру и скачать `kib-02-audit.json`. Проверить поля `summary`, `results` и `policy_version`.

У демонстрационных данных нет реальных IP-адресов и производственных секретов. Все устройства и разрешения придуманы для учебной проверки.

## Проверка качества

В папке [`tests/cases/`](tests/cases/) находится 20 независимых JSON-конфигураций. Рядом лежит [`tests/expected.json`](tests/expected.json) с ожидаемыми кодами политики и статусами. Скрипт [`tests/run.mjs`](tests/run.mjs) загружает каждый файл и сравнивает результат аудита с эталоном. Совпадение по одному только количеству нарушений не считается успешным тестом: должны совпасть ID, пункт политики и статус каждой записи.

В [`docs/test_results.md`](docs/test_results.md) приведены результаты автоматической проверки: **20/20 основных сценариев** и **32/32 дополнительных проверок**. Для этого тестового набора получены `FP = 0` и `FN = 0`. Эти показатели относятся к подготовленным учебным данным и не показывают качество работы на реальной инфраструктуре. Команда `npm test` повторяет проверку и выводит результаты в терминал; для обновления самого отчета используется `npm test -- --report`.

Отдельно предусмотрены проверки некорректных файлов: отсутствующих устройств, повторяющихся ID, ошибок формата, неподдерживаемых портов, размера файлов и других граничных случаев. Результаты ручной проверки интерфейса находятся в [`docs/browser_checks.md`](docs/browser_checks.md), модель угроз — в [`docs/threat_model.md`](docs/threat_model.md).

## Ограничения

Аудитор работает с подготовленным описанием сети, поэтому он **не сканирует устройства**, не подключается к промышленным контроллерам и не читает конфигурации настоящих межсетевых экранов. По его результатам нельзя сделать вывод о фактической доступности оборудования.

Аудитор учитывает явно записанные разрешения и одну фиксированную учебную политику. Приложение не моделирует маршрутизацию, NAT, состояние соединений, порядок ACL и частичные пересечения правил. Два разрешения через DMZ также не означают, что между их крайними точками появился отдельный сквозной доступ. Для него нужна самостоятельная запись во входном файле.

Результат `PASS` означает соответствие правилам модели `KIB-02/1.0`, а не гарантию безопасности промышленной сети. Итоговый отчет нужен для учебного разбора конфигурации и не заменяет аудит реальной инфраструктуры.
