# Руководство пользователя веб-приложения «Аудитор сегментации IT/OT-сетей»

**Учебный проект KIB-02**

Учебное веб-приложение для проверки правил доступа между устройствами офисной и промышленной сети. Оно рассчитано на системного администратора небольшого производственного предприятия, которому нужно просмотреть конфигурацию и найти разрешения, не соответствующие принятой политике сегментации.

Для работы не требуется подключаться к реальным коммутаторам, межсетевым экранам или контроллерам. Пользователь загружает подготовленное описание сети, а программа проверяет явно заданные в нём соединения. Все исходные данные проекта синтетические.

## Как запустить приложение

Приложение можно запустить через локальный сервер разработки Vite или собрать в один HTML-файл и открыть его в браузере. Первый способ удобен для работы с исходным кодом, второй — для демонстрации программы без запущенного сервера.

В обоих случаях для первоначальной установки и сборки нужен [Node.js](https://nodejs.org/) версии **24 или новее**. npm устанавливается вместе с Node.js. Git можно установить с [официального сайта](https://git-scm.com/downloads) либо скачать исходники без него через GitHub.

### Вариант 1. Запуск из исходного кода

На **Windows** команды выполняются в PowerShell, Windows Terminal, командной строке (cmd) или Git Bash. На **macOS** и **Linux** можно использовать обычный Терминал. Если Git или Node.js только что установлены, сначала закройте и снова откройте окно терминала.

Проверьте доступность инструментов:

```bash
git --version
node --version
npm --version
```

Перейдите в папку, где хотите разместить проект, и выполните:

```bash
git clone https://github.com/anastimaa/kib-02-ot-auditor.git
cd kib-02-ot-auditor
npm ci
npm run dev
```

`git clone` скачивает репозиторий, `npm ci` устанавливает зависимости из `package-lock.json`, а `npm run dev` запускает локальный сервер Vite.

После запуска в терминале появится адрес приложения, обычно **http://127.0.0.1:5173/**. Откройте его в браузере. Пока вы работаете с приложением, окно терминала нужно оставить открытым. Для остановки сервера нажмите `Ctrl+C`.

На Windows PowerShell иногда запрещает запуск файла `npm.ps1`. В этом случае откройте **cmd** или используйте команды `npm.cmd ci` и `npm.cmd run dev`. Изменять системную политику выполнения скриптов не требуется.

**Запуск без Git.** Откройте [страницу проекта](https://github.com/anastimaa/kib-02-ot-auditor), нажмите **Code → Download ZIP** и распакуйте архив. Откройте терминал в папке `kib-02-ot-auditor` с файлом `package.json` и выполните:

```bash
npm ci
npm run dev
```

### Вариант 2. Автономная HTML-версия

Автономная версия создаётся из исходного кода при сборке проекта. В результате появляется файл `dist/offline.html`, в котором находятся интерфейс, стили, JavaScript-код и встроенные демонстрационные конфигурации. Готовый файл открывается обычным двойным нажатием без локального сервера.

1. Скачайте проект командой `git clone` или через **Code → Download ZIP**, как описано в первом варианте.
2. Откройте терминал в корне проекта, где находится `package.json`.
3. Выполните команды:

   ```bash
   npm ci
   npm run build
   ```

4. Перейдите в созданную папку `dist/` и откройте файл `offline.html` в Chrome, Firefox, Edge или Safari.

Сборка выполняется один раз: после неё для открытия **готового `offline.html`** уже не требуются Node.js, npm и работающий сервер. Этот HTML-файл можно перенести на другой компьютер и запустить там. На Windows, macOS и Linux порядок одинаковый.

Папка `dist/` не хранится в GitHub-репозитории: она создаётся на компьютере после `npm run build`. Поэтому сразу после скачивания исходников из GitHub автономного HTML-файла ещё нет.

### Проверка тестов и сборка

Все команды выполняются из корня проекта:

```bash
npm test
npm test -- --report
npm run build
```

- `npm test` проверяет 20 учебных сценариев и дополнительные случаи, выводит результат в терминал, но не изменяет файл отчёта.
- `npm test -- --report` проводит те же проверки и **перезаписывает** `docs/test_results.md` актуальными результатами.
- `npm run build` проверяет TypeScript, собирает сайт в `dist/` и создаёт `dist/offline.html`.

Для просмотра обычной собранной версии через локальный сервер предусмотрена команда `npm run preview`. После её запуска откройте адрес, который выведет Vite.

## Что проверяет аудитор

Рассматривается небольшое предприятие с тремя сетевыми зонами:

| Зона | Что в ней находится | Зачем она выделена |
|---|---|---|
| `IT` | Офисные компьютеры и серверы | Работа сотрудников и обычные корпоративные сервисы |
| `DMZ` | Промежуточный сервер доступа | Контролируемые соединения между офисной и промышленной частью сети |
| `OT` | PLC, HMI, инженерная станция, архив технологических данных | Управление оборудованием и работа производственных систем |

Входной файл содержит список устройств и правила, которые разрешают (`allow`) или запрещают (`deny`) соединения между ними. Аудитор рассматривает каждое явно разрешённое соединение и сравнивает его с учебной политикой `KIB-02/1.0`.

Например, прямой доступ офисного компьютера к PLC по TCP/502 относится к нарушениям. А обращение согласованной рабочей станции к серверу доступа в DMZ по TCP/443 соответствует заданному исключению. В обоих случаях программа смотрит не только на порт: имеют значение зона, тип и точный идентификатор устройства.

Результат проверки одного разрешения может быть трёх типов:

| Статус в отчёте | Обозначение в интерфейсе | Что означает |
|---|---|---|
| `PASS` | Допустимо | Соединение совпало с разрешённым исключением учебной политики |
| `VIOLATION` | Нарушение | Правило противоречит политике сегментации |
| `REVIEW` | На проверку | Данных политики недостаточно для автоматического одобрения либо обнаружено точное противоречие между `allow` и `deny` |

`REVIEW` не считается разрешением. Программа предлагает уточнить такое правило вручную.

## Как устроена проверка

### Входные данные

**JSON** содержит пять обязательных полей: `schema_version`, `network_name`, `zones`, `assets`, `access_rules`. Поддерживается версия схемы `1.0`. Пример полного файла находится в [`examples/plant.json`](examples/plant.json).

Фрагмент одного правила из этого файла:

```json
{
  "id": "R-01",
  "source": "PC-01",
  "destination": "PLC-01",
  "protocol": "TCP",
  "port": 502,
  "action": "allow"
}
```

Это только одна запись из `access_rules`, а не отдельная конфигурация для импорта. Чтобы загрузить JSON самостоятельно, нужен полный объект с устройствами и зонами.

Для **CSV** требуются два файла в UTF-8. В `assets.csv` указаны устройства, а в `rules.csv` — правила доступа. Заголовки должны совпадать с примерами:

`assets.csv`:

```csv
id,name,zone,type
PC-01,Рабочая станция,IT,workstation
PLC-01,Контроллер,OT,plc
```

`rules.csv`:

```csv
id,source,destination,protocol,port,action
R-01,PC-01,PLC-01,TCP,502,allow
```

При загрузке CSV зоны определяются по столбцу `zone`. Система проверяет, что каждый источник и получатель существует в списке устройств. Максимальный размер каждого файла — **1 МиБ**. Допустимы от 1 до 200 устройств и до 1000 правил. Подробные ограничения описаны в [`docs/specification.md`](docs/specification.md).

### Порядок применения политики

Каждое явно разрешённое соединение проходит одну и ту же последовательность проверок. Срабатывает первое подходящее условие, поэтому у одного разрешения будет один код политики и один статус.

| Код | Когда применяется | Результат |
|---|---|---|
| `C-01` | У разрешения есть точный `deny` с теми же условиями | `REVIEW` |
| `P-06` | Источник `ANY` обращается к PLC | `VIOLATION` |
| `P-01` | Прямой доступ из IT к PLC | `VIOLATION` |
| `P-08` | Используется `ANY` или диапазон портов | `VIOLATION` |
| `P-03` | Согласованный доступ `PC-01 → JUMP-01`, TCP/443 | `PASS` |
| `P-04` | Доступ из `JUMP-01` к `ENG-01` по TCP/3389 или к `HIST-01` по TCP/443 | `PASS` |
| `P-05` | Доступ `HMI-01` или `ENG-01` к `PLC-01` по TCP/502 | `PASS` |
| `P-02` | Другое межсегментное разрешение | `VIOLATION` |
| `P-07` | Другое разрешение внутри одного сегмента | `REVIEW` |

Исключения `P-03`–`P-05` действуют только при совпадении идентификаторов устройств, их зон, типов и сервиса. Если в конфигурации появится похожее устройство с другим ID, разрешение не станет автоматически допустимым.

Запреты `deny` не образуют отдельные строки аудита: они нужны для проверки точного конфликта с `allow` и попадают в соответствующий раздел экспортируемого JSON. Частичные пересечения правил и их порядок в настоящем межсетевом экране программа не анализирует.

### Повторение демонстрации

Если нужно быстро проверить работу приложения, достаточно следующего сценария:

1. Открыть «Обзор аудита» с `plant.json` и проверить числа **3 / 5 / 1** для нарушений, допустимых соединений и ручной проверки.
2. Выбрать `R-01` и посмотреть, почему прямой доступ IT → PLC получил `P-01`.
3. В блоке «Конфигурация» выбрать «Без нарушений». Результат должен измениться на **0 / 5 / 0**.
4. Нажать «Загрузить конфигурацию» и выбрать из `examples/` два файла `assets.csv` и `rules.csv` одновременно. Они должны дать те же результаты, что и `plant.json`.
5. Вернуться к исходному примеру и скачать `kib-02-audit.json`. Проверить поля `summary`, `results` и `policy_version`.

У демонстрационных данных нет реальных IP-адресов и производственных секретов. Все устройства и разрешения придуманы для учебной проверки.

## Проверка качества

В папке [`tests/cases/`](tests/cases/) находится 20 независимых JSON-конфигураций. Рядом лежит [`tests/expected.json`](tests/expected.json) с ожидаемыми кодами политики и статусами. Скрипт [`tests/run.mjs`](tests/run.mjs) загружает каждый файл и сравнивает результат аудита с эталоном. Совпадение по одному только количеству нарушений не считается успешным тестом: должны совпасть ID, пункт политики и статус каждой записи.

В [`docs/test_results.md`](docs/test_results.md) приведены результаты автоматической проверки: **20/20 основных сценариев** и **32/32 дополнительных проверок**. Для этого тестового набора получены `FP = 0` и `FN = 0`. Эти показатели относятся к подготовленным учебным данным и не показывают качество работы на реальной инфраструктуре. Команда `npm test` повторяет проверку и выводит результаты в терминал; для обновления самого отчёта используется `npm test -- --report`.

Отдельно предусмотрены проверки некорректных файлов: отсутствующих устройств, повторяющихся ID, ошибок формата, неподдерживаемых портов, размера файлов и других граничных случаев. Результаты ручной проверки интерфейса находятся в [`docs/browser_checks.md`](docs/browser_checks.md), модель угроз — в [`docs/threat_model.md`](docs/threat_model.md).

## Ограничения

Программа работает только с подготовленным описанием сети. Она **не сканирует устройства**, не читает конфигурации настоящих межсетевых экранов и не проверяет физическую доступность PLC.

Аудитор учитывает явно записанные разрешения и одну фиксированную учебную политику. Приложение не моделирует маршрутизацию, NAT, состояние соединений, порядок ACL и частичные пересечения правил. Два разрешения через DMZ также не означают, что между их крайними точками появился отдельный сквозной доступ. Для него нужна самостоятельная запись во входном файле.

Результат `PASS` означает соответствие правилам модели `KIB-02/1.0`, а не гарантию безопасности промышленной сети. Итоговый отчёт нужен для учебного разбора конфигурации и не заменяет аудит реальной инфраструктуры.
